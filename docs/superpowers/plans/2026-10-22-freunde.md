# Freunde: Teilen von Kalender, Stundenplan und Aufgaben – Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Nutzer verknüpfen sich per Benutzername, geben pro Freund Kalender/Stundenplan/Aufgaben frei, sehen Freunde read-only, blenden deren Termine im eigenen Kalender ein und übernehmen Termine; private Termine bleiben unsichtbar.

**Architecture:** Zwei neue Tabellen (`friendships`, `shares`) plus Spalte `events.private`, in beiden Speichern (`SqliteStore`, `SupabaseStore` in `store.py`). Neue Endpunkte in `main.py` prüfen Freundschaft + Freigabe serverseitig und filtern private Termine und Notizen. Das Frontend bleibt eine Datei (`app.js`, IIFE-Muster) mit zwei neuen Views (`view-friends`, `view-friend`).

**Tech Stack:** FastAPI + Pydantic, SQLite / Supabase (PostgREST über httpx), Vanilla JS, CSS.

**Spec:** `docs/superpowers/specs/2026-10-22-freunde-design.md`

## Global Constraints

- Fremddaten nur bei `status = 'accepted'` UND passender Freigabe `shares(owner_id = Freund, viewer_id = ich)`; sonst immer `404` mit `"Nicht gefunden."`.
- Freundes-Termine enthalten genau `id, title, start_date, end_date, start_time, end_time, color, icon`; nie `note`, nie `private`.
- Private Termine (`private = true`) erscheinen nie in Freundes-Endpunkten.
- Neue Freigaben starten mit `calendar = timetable = todos = false`.
- Anfragen: höchstens 20 pro Stunde und Nutzer → `429 "Zu viele Anfragen. Bitte später nochmal."`.
- Der Assistent (`/api/chat`-Werkzeuge) bekommt keinen Zugriff auf Freundesdaten.
- Benutzernamen werden wie beim Login kleingeschrieben verglichen (`username.lower()`).
- Jede Frontend-Änderung zählt `CACHE` in `sw.js` und alle `?v=` in `index.html` um eins hoch.
- Commit-Footer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

- Anfrage an jemanden, der mich schon angefragt hat → wird sofort angenommen statt Fehler (Test in Task 2).
- Freund entfernt mich, während ich seinen Kalender offen habe → nächster Abruf `404`, Frontend zeigt „Nicht mehr verfügbar“ und springt zur Freundesliste zurück (Task 6, Schritt „404 behandeln“).
- Termin wird nachträglich privat geschaltet → verschwindet beim Freund beim nächsten Abruf (Test in Task 3).
- Groß-/Kleinschreibung beim Benutzernamen (`Max` vs `max`) → findet denselben Nutzer (Test in Task 2).
- Eingeblendeter Freund nimmt Kalender-Freigabe zurück → Bubble verschwindet, gespeicherte Einblendung wird ignoriert, keine Fehlermeldung im eigenen Kalender (Task 7).

**Files:**

**Interfaces:**
- Produces (Store, beide Klassen, als Modulfunktionen exportiert):
  - `get_friendship(a: int, b: int) -> dict | None` – Zeile `{id, requester_id, addressee_id, status}` unabhängig von der Richtung
  - `create_friendship(requester_id: int, addressee_id: int) -> dict` – `status='pending'`
  - `accept_friendship(requester_id: int, addressee_id: int) -> None` – setzt `accepted` und legt beide `shares`-Zeilen mit allem `False` an
  - `delete_friendship(a: int, b: int) -> bool` – löscht Freundschaft und beide `shares`-Zeilen
  - `list_friendships(user_id: int) -> list[dict]` – alle Zeilen mit `user_id` als requester oder addressee
- Produces (API):
  - `GET /api/friends` → `{"friends": [{id, username, they_share, i_share}], "incoming": [{id, username}], "outgoing": [{id, username}]}`; `they_share`/`i_share` = `{calendar, timetable, todos}` (Task 3 füllt sie; hier aus `get_share`, Standard alles False)
  - `POST /api/friends/request {username}` → `201 {status: "pending"|"accepted"}`
  - `POST /api/friends/{user_id}/accept` → `200 {status: "accepted"}`
  - `DELETE /api/friends/{user_id}` → `200 {ok: true}`

Schema SQLite und Supabase:

```sql
create table if not exists friendships (
  id bigint generated always as identity primary key,   -- SQLite: INTEGER PRIMARY KEY AUTOINCREMENT
  requester_id bigint not null references users(id) on delete cascade,
  addressee_id bigint not null references users(id) on delete cascade,
  status text not null default 'pending' check (status in ('pending','accepted')),
  created_at timestamptz not null default now(),
  check (requester_id <> addressee_id)
);
create unique index if not exists uq_friend_pair on friendships (least(requester_id, addressee_id), greatest(requester_id, addressee_id));
-- SQLite: min(...), max(...) statt least/greatest
create table if not exists shares (
  owner_id bigint not null references users(id) on delete cascade,
  viewer_id bigint not null references users(id) on delete cascade,
  calendar boolean not null default false,
  timetable boolean not null default false,
  todos boolean not null default false,
  primary key (owner_id, viewer_id)
);
alter table friendships enable row level security;
alter table shares enable row level security;
grant all on friendships, shares to service_role;
grant all on all sequences in schema public to service_role;
```
